## Phases

- [x] **Phase 1 (done) — CORS + rate limit.** CORS policy matching `hrb_chatbot_v2`'s current `main.py` config. Redis-backed per-`employee_id` rate limiting (prerequisite: Redis live in production). Depends on `hrb_common_libs[observability,cache]`.
  - **Spec:**
    - **Context:** first real code in this repo. Everything downstream (Phase 2's RBAC, Phase 3's forwarding) sits behind this entry layer.
    - **Source:** CORS config is a direct port of `hrb_chatbot_v2`'s `main.py` (`allow_origins=["https://hrb-chatbot-ui.rvsree.dev"]`, `allow_origin_regex=r"http://localhost:\d+"`, `allow_credentials=True`, `allow_methods=["*"]`, `allow_headers=["*"]`). Rate limiting is new code - no equivalent exists in `hrb_chatbot_v2` today (flagged in NFR-review discussion as "already broken at real scale").
    - **Request/response contract:** rate-limit rejection returns `429` with the existing `{"error": ..., "code": "RATE_LIMITED"}` shape (`hrb_chatbot_v2`'s own `error_codes.py`/`api/dependencies.py::json_error` convention, replicated here since this service doesn't depend on `hrb_chatbot_v2`'s own code).
    - **API surface:** `configure_cors(app)`, `RateLimiter(redis_client, limit_per_minute=60)` with `.check(employee_id) -> bool`, a FastAPI dependency `enforce_rate_limit` that 429s when `.check()` returns False, `GET /ping` (process-up, no backend calls - same two-tier health convention as `hrb_chatbot_v2`).
    - **Failure modes:** CORS rejection is the browser's own job (no server-side code needed beyond correct headers). Rate-limit check failing open if Redis itself is unreachable (never block all traffic because Redis hiccuped) - logged as a warning, not silently swallowed.
    - **Out of scope:** RBAC (Phase 2), routing (Phase 3), contract validation (Phase 4).
    - **Open questions:** none blocking.

- [x] **Phase 2 (done) — RBAC, absorbing rbac.py.** Port `require_role()`'s contract from `hrb_chatbot_v2`'s `api/gateway/rbac.py` - 401 if `user_profile` missing/invalid role, 403 if role not permitted on the route. Identity stays self-asserted (unsigned `user_profile` in the body) - real OAuth2 is a deliberately separate, later phase, not bundled here.
  - **Spec:**
    - **Context:** absorbing, not duplicating - once this is live, `hrb_chatbot_v2`'s `api/gateway/` package is deleted from the (split) backend repos, per the Decisions doc's own ruling. Two places checking the same role claim is how one of them goes stale.
    - **Source:** direct port of `hrb_chatbot_v2`'s `api/gateway/rbac.py::require_role()`/`identity_from_query_params()`, plus the `UserProfile` model (`models/common.py`) and `Role` enum (`common/enums.py`) it depends on - ported as this repo's own copies since it doesn't import `hrb_chatbot_v2`'s code.
    - **Request/response contract:** 401 if `user_profile` missing or its `role` isn't a real `Role` value; 403 if the role isn't one of the route's allowed roles. Identical status codes/detail-message shape to the original.
    - **API surface:** `UserProfile` (pydantic model), `Role` (StrEnum: employee/manager/hr_support/admin/employee_admin), `require_role(user_profile, *allowed_roles) -> UserProfile`, `identity_from_query_params(...)` for the three GET routes that can't carry a body (Fetch spec forbids it on GET/HEAD - same Phase 96 reasoning as the original).
    - **Behavior parity:** ported with no logic changes - same status codes, same detail-message shape.
    - **Out of scope:** real OAuth2/signed identity (unwired placeholder in `hrb_chatbot_v2` today, a deliberately separate later phase - see Decisions). Route-level wiring of `require_role()` into actual forwarded routes (Phase 3, once there's something to forward to).
    - **Open questions:** none blocking.

- [x] **Phase 3 (done, single-backend) — route-to-service forwarding.** Plain env-var URL map (`RAG_INGESTION_SERVICE_URL`, `RAG_RETRIEVAL_SERVICE_URL`, ...), same pattern as `HRB_LMS_MCP_URL`. Forwards request body/headers + adds `request_id`.
  - **Spec:**
    - **Context:** `hrb_rag_ingestion_service`/`hrb_rag_retrieval_service` don't exist yet - this phase builds generic forwarding against one configurable backend, so it can be proven against the still-undivided `hrb_chatbot_service` today (per the original cutover plan - Phase 5 points the real frontend at the Gateway, forwarding 1:1 to one backend, before any RAG split happens). The route-to-*multiple*-services map becomes real config once those services exist - the forwarding mechanism itself doesn't need to wait.
    - **Source:** new code. `request_id` generation reuses `hrb_common.observability`'s `new_request_id()`/`set_request_id()` from Phase 1 of `hrb_common_libs`.
    - **Request/response contract:** forwards method/path/query/body/headers unchanged except `X-Request-ID` added; returns the backend's response unchanged (status code, body, most headers) - no reshaping, no aggregation (explicitly out of scope per the Decisions doc).
    - **API surface:** `forward_request(request: Request, backend_base_url: str) -> Response` - a generic reverse-proxy function; `BACKEND_SERVICE_URL` env var for the single-backend case this phase actually covers.
    - **Failure modes:** backend unreachable → Resiliency's `CircuitBreaker` (from `hrb_common.observability`) trips after repeated failures → `503` with `{"error", "code": "BACKEND_UNAVAILABLE"}`, not a hung connection.
    - **Out of scope:** the real multi-service route map (Phase 3 extended, once `hrb_rag_ingestion_service`/`hrb_rag_retrieval_service` exist) - this phase proves the mechanism against one backend. Response aggregation across backends (still conditional on more backends existing, per the Decisions doc).
    - **Open questions:** none blocking.

- [x] **Phase 4 (done) — contract validation.** Validate outbound body against target backend's declared Pydantic schema before forwarding; 422 at the Gateway on mismatch. 38/38 tests pass. Live-verified: invalid body cleanly rejected (`422`/`VALIDATION_ERROR`, never reaches the backend); valid body forwards through to the real running backend.
  - **Spec:**
    - **Context:** user-directed, 2026-10-21 - chose "import `hrb_chatbot_service`'s Pydantic models" over duplicating or dynamic-OpenAPI validation, then switched to duplicate-schemas once the real cost of "import" was found: `hrb_chatbot_service` has no `pyproject.toml`/`setup.py` at all today - every file imports via `from src.hrb_chatbot....`, which only resolves when run from that repo's own root, not as an installed package (its own CLAUDE.md: "never run from inside src/" - a deliberate choice, not an oversight). A real import dependency would mean restructuring hundreds of files' imports in the main production backend just to serve this Gateway's validation need - rejected as disproportionate. Duplicate schemas is the same pattern Phase 2 already used for `UserProfile`/`Role` - this repo's own established, accepted way of staying import-independent from `hrb_chatbot_service`.
    - **Source:** new code - `gateway/contracts.py` duplicates (not imports) the request-side shape of `RagQueryRequest`/`AgenticRagRequest`/`MultiAgenticRagRequest` from `hrb_chatbot_v2/src/hrb_chatbot/models/{rag,agentic_rag,multi_agentic_rag}.py` as of 2026-10-21 (post Phase 244's `guardrails_model` field), read directly rather than guessed.
    - **Request/response contract:** no change to the real backend's own contract - this is a Gateway-side pre-check only. A body that fails validation against the matching model gets `422` with the existing `{"error": ..., "code": "VALIDATION_ERROR"}` shape (`gateway/error_codes.py`/`responses.py::json_error`), same convention as every other Gateway error - never forwarded to the backend at all.
    - **API surface:** `gateway/contracts.py` - `PATH_TO_MODEL: dict[str, type[BaseModel]]` mapping exactly 3 paths (`/v1/genai-rag-retrieval/query`, `/v1/single-agentic-rag-retrieval/query`, `/v1/multi-agentic-rag-retrieval/query`) to their duplicated request models; `validate_contract(path: str, body: bytes) -> None` - no-op (returns immediately) for any path not in the map, raises `pydantic.ValidationError` for a known path with an invalid body. Wired into `main.py`'s `forward_to_backend` route, called before `forward_request()`.
    - **Failure modes:** a `ValidationError` is caught in `main.py` and turned into the `422`/`VALIDATION_ERROR` response described above. A path outside the 3 known ones is forwarded unvalidated, unchanged from today's behavior - not a failure, a deliberate scope boundary (see below).
    - **Out of scope:** validating every other endpoint this backend exposes (ingestion, auth, feedback, conversations, admin, faq, interview-qa, ...) - scoped to the 3 query endpoints only, since those are what the real frontend actually calls and what Phase 5's own cutover needs proven first. Widening to the full endpoint surface is a real, separate fast-follow, not silently assumed done here. No automatic drift detection between the Gateway's copy and the backend's real model (same accepted risk Phase 2 already carries for `UserProfile`/`Role`) - a schema change on the backend side needs a matching manual update here, not caught automatically. The duplicated models use plain `str`/`float`/`int` for fields the real backend constrains with an enum (`SearchStrategy`, `VectorDB`, `LlmProvider`) - catches missing/malformed fields and wrong nesting, not an invalid-but-right-typed enum value (e.g. `search_strategy: "not_a_real_strategy"` passes the Gateway's check, still gets a real `422` from the backend itself). A deliberate simplification, not a gap in defense-in-depth - the backend is still the authoritative final validator either way.
    - **Open questions:** none blocking - scope explicitly narrowed and confirmed via the same decision that picked duplicate-schemas over import.

Every forwarded query 503'd until this was fixed - bumped to 90s. 38/38 tests still pass (none exercise real backend latency). Re-verified live: a real forwarded query now returns 200 with a real grounded answer.

  - `BACKEND_SERVICE_URL` points at the real production `hrb_chatbot_service` (`https://hrb-chatbot.rvsree.dev`) - `hrb_chatbot_ui` itself is NOT yet pointed at this Gateway (that half of "cutover" - switching the real frontend's own `API_BASE_URL` - is a separate, smaller follow-up, flagged not done here).

- [x] **Phase 6 (done) — `/health` endpoint.** 27/27 tests pass. Live-verified against the running server: real Redis check correctly reports unhealthy (no local Redis running - a known, separate gap, not a bug introduced here), `backend_service` check correctly reports healthy against `hrb_chatbot_service` on :8093. This repo only has `GET /ping` today (Phase 1) - a flagged gap found while updating `hrb_chatbot_service`'s own status board. Add the same two-tier convention `hrb_chatbot_v2` already uses.
  - **Spec:**
    - **Context:** `hrb_chatbot_v2`'s own CLAUDE.md documents "two endpoints, not a toggle" as a settled convention (`/ping` = process-up, instant; `/health` = one real, free call per backend, never raises). This Gateway shipped `/ping` in Phase 1 but never the `/health` half - this phase closes that gap, same convention, not a new one.
    - **Source:** new code - `gateway/health_checks.py`, modeled directly on `hrb_chatbot_v2`'s `api/admin/health_checks.py` (`check_*()` functions returning `{"status": "healthy"|"unhealthy", "message": str}`, never raising; an aggregator combining them into one overall `status`).
    - **Request/response contract:** `GET /health` (no identity required, same as `hrb_chatbot_v2`'s own `/health` - this is an ops/monitoring endpoint, not a user-facing one). Response: `{"status": "healthy"|"unhealthy", "checks": {"redis": {...}, "backend_service": {...}}}`, each check the same `{"status", "message"}` shape. `200` when every check is healthy, `503` otherwise - same `health_response()`-style mapping as the original.
    - **API surface:** `check_redis() -> dict` (real `PING` via `hrb_common.cache.connection.get_redis_client()`), `check_backend_service(backend_base_url: str) -> dict` (real `GET {backend_base_url}/ping`, 5s timeout - the backend's own cheap `/ping`, not its `/health`, so this doesn't cascade into the backend's own full health check), `check_all() -> dict` (aggregator), wired into `main.py` as `GET /health`.
    - **Failure modes:** Redis unreachable → `{"status": "unhealthy", "message": "<error>"}` for that check only (distinct from the rate limiter's own fail-open behavior - `/health` is for an operator to see the real state, so it must report unhealthy, not hide it). Backend unreachable/non-200 → same shape for `backend_service`. Neither check ever raises - `/health` itself always returns 200 or 503 with a real body, never a 500.
    - **Out of scope:** no new identity/auth on this route (matches `/ping` and the original `hrb_chatbot_v2` convention - ops endpoints, not gated by RBAC). Not wired into Docker `HEALTHCHECK`/CI smoke tests in this phase (still `/ping`, unchanged) - this phase only adds the endpoint.
    - **Open questions:** none blocking.

- [x] **Phase 7 (done) — `/health` surfaces real backend health (embedding_model etc.), reversing Phase 6's cheap-check choice.** 28/28 tests pass. Live-verified: `GET /health` now nests the real backend report (`embedding_model`, LLM/vector/metadata detail) under `checks.backend_service.backend_report`; `hrb_chatbot_ui`'s `getHealth()` updated to read either shape (direct-backend today's prod default, or Gateway-nested for local dev), since Phase 5's cutover hasn't happened yet and both are live today. Real regression found immediately after Phase 6 shipped: `hrb_chatbot_ui`'s Settings → Model tab reads `embedding_model` from `GET {API_BASE_URL}/health` - with the frontend pointed at this Gateway (not the backend directly), that call now hits THIS repo's own Phase 6 `/health`, which has no `embedding_model` field at all (it only ever reported Redis/backend-reachability, by design). The field silently stopped rendering - caught via a live screenshot, not guessed.
  - **Spec:**
    - **Context:** Phase 6's own spec explicitly chose `GET {backend}/ping`, not `/health`, specifically "so this doesn't cascade into the backend's own full health check" (a real LLM/vector-store/metadata-store call, not free). That reasoning was correct in isolation but missed that the frontend already depended on `/health` specifically for backend detail the Gateway's own cheap check can't provide - this phase reverses that one call, with the tradeoff now explicit rather than accidental.
    - **Source:** `gateway/health_checks.py::check_backend_service()` - change the call from `GET {backend_base_url}/ping` to `GET {backend_base_url}/health`, capture the full JSON body (not just the status code).
    - **Request/response contract:** `GET /health`'s own response shape gains one field: `checks.backend_service` changes from `{"status", "message"}` to `{"status", "message", "backend_report": <the backend's full /health JSON>}` - `backend_report` is `null` when the backend call itself failed (connection error, non-200, bad JSON), so a caller can't mistake a missing report for an empty-but-successful one. `hrb_chatbot_ui`'s `getHealth()` (`src/api/client.ts`) updates its one call site to read `response.checks.backend_service.backend_report?.embedding_model` instead of `response.embedding_model`.
    - **API surface:** `check_backend_service(backend_base_url, client=None) -> dict` - same signature, same optional-client testability convention as Phase 6/`forward_request`; its own `status` is still derived from "did the call succeed and return 200", not from the backend's own reported `status` (so a backend self-reporting `unhealthy` - e.g. a down vector DB - doesn't need a second layer of interpretation here; the Gateway only measures "could I reach it and get a 200," same bar `/ping` used).
    - **Failure modes:** unchanged shape-wise from Phase 6 on a connection error/non-200 (`backend_report: null`), just a (small, already-paid-for-elsewhere) latency/cost increase on every Gateway `/health` call, since it's now a real LLM-provider call every time, not a free ping.
    - **Out of scope:** no change to `GET /ping` (still instant, no backend call, Docker/CI still point at it). No change to the Gateway's own `redis` check. Not caching the backend health result between calls (`/health` is an ops-diagnostic endpoint, expected to be called rarely, not on a hot path) - a real but minor, deliberately accepted cost, not revisited here.
    - **Open questions:** none blocking - this is a direct, scoped fix for a live-confirmed regression, not a new design.
